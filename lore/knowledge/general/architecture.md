# Planner architecture standard

These rules describe the code as it is. ADR-0010 records the crate rules; this node is the working summary agents read before touching a crate.

## Crates and dependencies

- **Three contexts, one crate each: planning, identity, activity.** The server (`reeve-server`) is the only composition root; the CLI (`reeve`) depends on `reeve-protocol` and HTTP only. Reason: parallel agents can work one context without colliding, and nothing but the server decides how contexts are wired.
- **Ports are defined by the consumer.** `reeve-activity` implements planning's `ActivitySink` and identity's `IdentityActivity`, so it depends on `reeve-planning` and `reeve-identity`, never the reverse. Adapters are `pub(crate)` behind factories that return trait objects: `Arc<dyn Trait>` for a context with one port (`make_token_store`, `make_activity_store`), and a bundle for a context with several, `make_planning_ports` (returning `PlanningPorts`, one `Arc<dyn …>` per aggregate port, all views of one `PgPlanningRepo`). `scripts/check-context-isolation.sh` enforces facade imports (`reeve_planning::Thing`, never `reeve_planning::repo::Thing`). Reason: the supplier can be replaced or tested without the consumer noticing, and the lint keeps the boundary from eroding.
- **Planning has one port per aggregate, placed by six rules.** (1) A method that reads or writes one aggregate's own rows and joins no other aggregate's table goes on that aggregate's trait (`InitiativeRepo`, `EpicRepo`, `StoryRepo`, `DecisionRepo`, `CommentRepo`, `PullRequestRepo`, `SprintRepo`). (2) A read that joins other aggregates' tables (readiness, counts, views, search, batch lookups for lists, the export readers) goes on `PlanningReads`. (3) The key sequence and every key or external-reference lookup across item types go on `KeyRepo`. (4) `PullRequestRepo` has no method that writes delivery, resolution or a story's version. (5) An urgent mark's own reads and writes go on `UrgencyRepo`: the mark is stored on the marked initiative's, epic's or story's row but is no field of those aggregates and never changes their version, so it is on none of their traits; the lineage read that spreads it (`urgency_lineage_in`, joining epics and stories) follows rule 2. Attachments follow rule 1 (`AttachmentRepo`: their own rows and chunks, the claim, the sweep), and their export reader follows rule 2 (`PlanningReads::attachments_in`). (6) A promise's four columns on a story or epic row are written only through `PromiseRepo` (`lock_for_promise`, `set_promise`, `clear_promise`) and read through `lock_for_promise` (under the lock), `PlanningReads::promise_facts_in` and `promised_between_in` (rule 2: they join stories and epics); the clock's active and draft sprints come from `SprintRepo::active_and_draft_in`, which reads only sprints (rule 1); they are no field of `Story` or `Epic`, and moves never read or write them (the lint bans those names, `ports.promises`, `promise_clock_in` and the set/clear entries in `handler/moves.rs`). Reason: a port the size of the context hides which code can change what, while one sequence keeps keys unique across item types (kb/ADR-0002 R5, kb/ADR-0002 R4), and a mark that no item port can write cannot change an item (kb/ADR-0017 R1, R5), and a promise that no item or move path can touch gates nothing (kb/ADR-0025 R2, R7).
- **DTO builders live in `handler/dto.rs`; `domain/` names no `*Dto`.** The lint refuses an identifier ending in `Dto`, and `StoryWithReadiness`, anywhere under `crates/reeve-planning/src/domain/`. Reason: the domain must not change when the wire does.
- **A use case that spans ports runs in one transaction.** The handler opens it and passes it to each mutating method; there is no unit-of-work object (kb/ADR-0010 R5). Reason: no change without its activity entry, and no read that mixes two states of the world.
- **Three call sites are fixed by the lint** (`scripts/check-context-isolation.sh`, cases in `scripts/tests/isolation.sh`): `set_delivery` and `move_to` are named only in `handler/moves.rs` (a call, UFCS or a method value); `handler/moves.rs` never reaches `ports.sprints`, `active_goals_of_stories`, `ports.urgency`, `urgency_lineage_in`, `urgency_in`, `ports.promises`, `promise_facts_in`, `promised_between_in`, `promise_clock_in`, `active_and_draft_in` or `set_promise`/`clear_promise` (and their `_in` forms); `handler/prs.rs` names the ports only as `ports.pull_requests.<method>` and `ports.stories.get_story` (no alias, no UFCS), and never calls `move_story`; with a `handler/mod.rs`, both files must exist. Reason: kb/ADR-0002 R4 (only `move_story` moves a story), kb/ADR-0014 R4 (moving never depends on goals), kb/ADR-0017 R5 (delivery never depends on urgency, and the webhook never reads or writes it) and kb/ADR-0025 R7 (delivery never depends on promises), held where a reviewer cannot miss them. The lint reads each file with string literals blanked and without comments and whitespace, so a call split over lines is still caught. It is a tripwire over source text, not a proof: a call routed through another handler method, or generated by a macro, escapes it; the behaviour itself is pinned by tests (`crates/reeve-planning/tests/rules.rs`, `tests/sprints.rs` `moves_never_depend_on_goals`, `tests/handlers.rs` `recording_a_pull_request_links_updates_and_never_moves_the_story`).
- **`reeve-testdb`: test support, not a context.** It is a dev-dependency of the crates' tests and depends on no context crate (the caller passes its migrator). Reason: every context's tests share one way to get a database without the contexts depending on each other.

## Transactions and time

- **Mutating port methods take the caller's `sqlx::Transaction`.** A mutation and its activity entry commit together, for planning and identity alike. Mutations that change an item's own content take a caller-supplied version and refuse a stale one with Conflict: the edits (initiative, epic, story), `move_story` and the discovery mark (including a re-mark that changes nothing). `edit_decision` also takes the caller's version (read `FOR UPDATE`, checked before the closed rule; an edit that changes nothing writes nothing). `link_record`, `close_decision`, `add_block`, `remove_block` (a missing edge is a no-op), comments and the creates take no caller version (creates are guarded by the idempotency key instead); `record_check` takes the decision version the checker observed and refuses a result for a reference that has changed since; a result equal to the stored one (`commit` ignored) only moves `checked_at`, with no activity entry and no version bump, so the scheduled run logs changes, not repetitions. `move_story` and the required-decision mutations also lock the row `FOR UPDATE`; the edit handlers (story, epic, initiative, discovery mark) read unlocked and rely on the version-guarded `UPDATE` returning Conflict when zero rows match. The move handler runs at `REPEATABLE READ` so readiness is computed from one snapshot. Events are published after commit: the event stream reads only committed activity rows (see below). Reason: no activity entry without its change, no lost update, and no readiness answer that mixes two states of the world.
- **Handlers own the clock and the actor:** `Ctx { actor, via, now, client }`. Repositories and domain code never read the time or the caller. `client` is a provenance string beside `via`: `None` for the API, the CLI and the webhook, and for an MCP caller the host of its connection's client id (the id itself when it has no host, as the developer command's); `Handlers::rec`, the one place an activity record is built, writes it into the entry's payload as `client` (kb/ADR-0029 R9), and the web's activity views, its live note and the TUI's ticker show it as "via <client>". Reason: tests fix the clock, the automation rule needs the actor in one place, and a write made from a chat must say which app made it.

## Domain

- **The delivery rule is `Story::move_to`; the required-decision rules are `RequiredDecision::{link, edit, record_check, close}`.** Both are in `domain/`, refuse with a typed error (`MoveRefused`, `DecisionError`) and leave the aggregate untouched when they refuse; the handlers load, call, persist and log. See [[domain/planning]]. Reason: a rule on the aggregate is tested without a database, and with private fields a second caller cannot skip it. Item edits (initiative, epic, story) still validate in the handler or a constructor and rebuild the item with `from_persisted`, which does not validate; see [[domain/planning]].
- **Readiness is a pure function over `ReadinessInput`.** Nothing derived is stored except a required decision's check result. Reason: a stored derivation goes stale; the one fact that needs git is cached explicitly.
- **Readiness facts are loaded by `readiness_inputs` for any number of stories in five statements, never per story.** Lists, story contexts and the decision queue (unfinished stories with readiness, active and draft goals, decision lineage, urgency, promise facts) read in one `REPEATABLE READ READ ONLY` snapshot; the readiness gate uses the same loader with one key. Blocking reasons and `blocked_by` both come out in key-number order. The loader returns every blocker with its delivery and owner and applies no policy; `blocks` decides (kb/ADR-0027 R5). Reason: the cost of a board must not grow with its story count, one loader cannot drift from a second copy of the rules, and a snapshot means a list never shows two states of the world.
- **The done window is a read-side filter on `stories.done_at`, with the cutoff computed by the handler.** `done_at` is set when a story moves to done and is NULL for stories imported already done; `GET /stories?done=recent|all|none` (default `all`): `recent` keeps stories done since the cutoff, `none` keeps no done story (the decision queue reads with `None`). The handler passes the repository a `DoneWindow { All, Since(cutoff), None }`, computing the cutoff from `c.now` and `[board] done_window_days` (default 14, 1..=3650), because repositories never read the clock. Initiative counts come from one grouped statement and ignore the window. Reason: the board stays small as done work accumulates, and the full history stays one parameter away.
- **The story list's filters split between SQL and the handler by what each may read (kb/ADR-0021).** `StoryRepo::list_stories` reads text (an `ILIKE` substring of title, description or external reference, escaped, or exactly the key the text names, which the handler derives with `key_named_by`; `Handlers::list_stories` takes the raw text and builds `StoryText` itself), kind, an epic set and the done window. The handler expands `initiative` to its epic keys (`EpicRepo::epic_keys_in`) in the same snapshot. `ready`, `goal`, `urgent` and `promised` apply after the read, on values computed in that snapshot. `urgent` is not SQL because the story port may not read mark columns (kb/ADR-0017: marks are read only through `UrgencyRepo`) and `urgency_in` is the one definition of what is urgent, so the filter keeps exactly the rows the response shows urgent. `promised` is not SQL for the same reason: the story port may not read promise columns, and `story_promise` (`domain/promise.rs`) is the one definition of a story's promise. Reason: one definition of each fact, and a filter that cannot disagree with the row it keeps.
- **Sprints and goals are planning data (`sprints`, `goals`, `goal_links`); moving a story never depends on them.** A sprint is a window `[opened_at, closed_at)`, at most one active, and stories carry no sprint field: a story counts in the one sprint whose window holds its completion, and a story started and unfinished at close is shown as in flight, never as done (kb/ADR-0014 R1, R2). Goals belong to one sprint and link to items by key; no delivery rule, readiness input or item progress reads them (per-goal counts do), and their actions are logged under their own names, never `override` (R3, R4). The web client's nudge on starting a story is client-side: it posts a separate link after the move and the move does not wait for it. Opening or closing a sprint, editing dates, goals, confidence and verdicts need an interactive token; automation and the system may only link, unlink and suggest a confidence (R5). Sprint and goal views, closed ones included, are computed on read; the counts at close live only in the sprint's `closed` activity entry, which the CLI and the web client compose beside the derived counts, and planning never reads it. "Blocked by decisions" is live for the active sprint and shown from the closed entry for a closed one. `[sprints] length_days` (default 14, 1..=90) and `upkeep_line` (default 20, 0..=100, a reference line, not a budget) are the only configuration. Reason: a stored membership or summary goes stale and a goal that gates a move would make planning a delivery rule (R6).
- **The header goal picker's linking mode is client state; linking writes only goal links.** `GoalPicker` lists the next and the active sprint's goals and adds goals to the draft; picking one starts linking mode, held in `goalPicker.svelte.ts` (it survives client-side navigation and ends on a reload), in which initiatives and epics show a `GoalLinkButton` that links or unlinks them, one write at a time followed by a sequenced reload. Reason: linking work to goals happens while browsing the plan, and a link is never a move or a readiness input (kb/ADR-0014 R4).
- **Urgent marks are columns read and written only through `UrgencyRepo` (`ports.urgency`), their lineage read through `PlanningReads::urgency_lineage_in`; item `UPDATE`s never name them, so no edit drops a mark; urgency is computed per snapshot (`handler/urgent.rs` `urgency_in`).** Reason: a mark that is not a field of `Initiative`, `Epic` or `Story` cannot be lost by an edit, and one computation per snapshot keeps every view of a lineage consistent (kb/ADR-0017).
- **Tokens are opaque random secrets with a `reeve_` prefix, stored as SHA-256 hashes; role is derived from configuration on every request.** Reason: a database leak yields no usable token, and a role change takes effect immediately.
- **A token carries an audience, `api` or `mcp`, and each audience authenticates through its own function (kb/ADR-0029 R5, R6).** The API, the event stream, attachments and the session cookie authenticate through `authenticate_api`, which refuses an MCP token; the `/mcp` endpoint authenticates through `authenticate_mcp` when `[mcp]` is enabled (off by default). The first returns a `Principal` and the second an `McpPrincipal`; there is no function that accepts both. `Caller` (the API's extractor) uses the first, `McpCaller` (bearer header only, never a cookie) the second, and both load the access policy on every request. The token listing and single revocation see API tokens only, while disabling a user revokes every audience (kb/ADR-0015 R6). An MCP token is always interactive and lives at most one hour (`issue_mcp_token`); `issue_token` and sign-in issue API tokens only. An MCP token belongs to a connection and is issued by `exchange_code`, `refresh_tokens` or the developer command `mcp-token-issue` (which makes a connection of its own, client `urn:reeve:developer-command`); `insert_token` writes API tokens only. Reason: a token issued for the MCP endpoint must work nowhere else, two types make handing the wrong caller to a handler a compile error, and the audience must not become a third token kind (kb/ADR-0015 R5, R7).
- **An MCP client finds where to sign in from two documents served outside the API router (kb/ADR-0029 R2, R11).** `crates/reeve-server/src/auth/oauth.rs` (which also holds what the OAuth routes share) serves `GET /.well-known/oauth-protected-resource/mcp` (RFC 9728) and `GET /.well-known/oauth-authorization-server` (RFC 8414) without a caller. They are always mounted, with the `[mcp]` switch inside the handler: off, each answers 404, and `[mcp] enabled` loads only with `[oidc]`, so an instance without sign-in answers 404 too. They are not in the OpenAPI document and never answer in the API's envelope. Every address in them is built from `ServerConfig::issuer()` (`public_url` without its trailing slash; `public_url` never has a path), because clients compare the issuer and the resource (`<issuer>/mcp`) as strings. A 401 from `/mcp` names the first document in `WWW-Authenticate: Bearer resource_metadata="…"`, with `error="invalid_token"` when a bearer token was presented and refused. `assets::serve` never treats a path under `/oauth/` or `/.well-known/` as a page: an unknown one is a plain 404, not `index.html`. The authorization server's document names `/oauth/authorize`, which answers (`auth/authorize.rs`, below), and `/oauth/token`, which answers too (`auth/token.rs`, below). Reason: Claude starts sign-in only from that 401, and a client that is handed a web page or a mismatching address in place of metadata fails without saying why.
- **An MCP client is identified by the address of a metadata document, resolved by one function (kb/ADR-0029 R3).** `reeve_identity::resolve_client(fetcher, policy, client_id, redirect_uri)` answers a `ValidatedClient` or a `ClientRefusal`, in this order: the client id keeps the rules of a client id (a URL with a host, no user information, a path, no query, no fragment, written exactly in its parsed form); its host is in `[mcp] client_hosts`; the redirect address equals, as text, an entry of `[mcp] redirect_uris`; only then are the document's bytes fetched; the document must keep its own rules; then the address must equal one of the document's own. An app the instance has not enabled therefore causes no outbound request, and `ClientRefusal::not_enabled` marks those two refusals. Nothing is cached: `GET /oauth/authorize` calls `resolve_client` on every request, and no other route does. The rules of a client id and of a document are the domain's, in `clients.rs`; the document type never leaves that file. The port `ClientDocumentFetcher`, defined beside `resolve_client`, has one method, `fetch(&Url) -> Vec<u8>`, and returns bytes only. Its one adapter holds the rules of transport: it refuses, before anything is sent, an address that is not https with a host name (never an address literal) and no port; uses no proxy and follows no redirect; resolves through a resolver that refuses the whole answer when any address is not public (IPv4 outside RFC 6890's special blocks; IPv6 only global unicast, minus its special parts) and hands the connector only checked addresses; accepts a 200 of at most 64 KiB within 5 seconds; and runs at most four fetches at once, refusing a fifth (the limit is the fetcher's, and the server shares one). `build_state` chooses the fetcher where `build_oidc` chooses the provider: `make_loopback_client_fetcher` (http on a loopback IP literal, no names resolved) for the static provider, which exists only under the test-only `static-oidc` feature, and `make_client_fetcher` otherwise; `validate` admits a loopback client host or an http redirect under that same condition only. Reason: the fetch is triggered by an anonymous request, so every step that could reach inside the network or hold the server is refused before anything is sent, and a client is judged by what it publishes at its own address, not by what the request claims.
- **A request to connect is held in memory from authorize to the exchange of its code, by one type in identity (kb/ADR-0029 R4, R11).** `reeve_identity::AuthorizationRequests` (one per process, in `AppState.authorization_requests`; at most 1000, ten minutes each) is opened only from a `ValidatedClient`, so no later step can redirect to an address that was not validated. `GET /oauth/authorize` (`crates/reeve-server/src/auth/authorize.rs`) checks the `[mcp]` switch, then validates in a fixed order: until the client and its redirect address are validated the browser goes to the page with `?problem=`, and after that a refusal goes back to the validated address with `error`, `state` and `iss`. It sets the cookie `__Host-reeve_connect` (`reeve_connect` on http), which holds the SHA-256 of the request's id, and sends the browser to the page `/connect?request=<id>`. The page reads the request through `GET /api/v1/connection-requests/{id}`, which hands out a one-time approval value stored with the id of the token that read it, and answers it through `POST …/approve` or `…/refuse`. Any interactive API token of the person may read and answer (an automation token is refused with 403, by one check in identity), as a session cookie (with the client header) or as a bearer header: `Caller` accepts any API token under the cookie's name, so the cookie is no boundary. The proofs are the token's kind, the connect cookie, and the approval value from the token that read the request; a request that is unknown, expired, answered or another browser's is one 404. `AuthorizationRequests::approve` checks the answer and gives the request its code in one step; `approve_request` then writes and commits `connection_approved` and only then returns the code, and forgets the request if the entry cannot be written. `redeem` checks a code against its client, redirect address, resource and PKCE verifier before it removes the request, so a wrong attempt spends nothing and a code works once. Once a request is approved only its code's minute decides, not the request's ten: a code approved late keeps its full minute. Every answer of `/oauth/authorize` says `Cache-Control: no-store` and `Pragma: no-cache` (the handler marks whatever it returns, the 404 of a switched-off instance and the 405 included), and so does every answer of the three API routes: their own middleware (`guard` in `routes/connection_requests.rs`) runs before any extractor, answers 404 when `[mcp]` is off without authenticating the caller or reading the path or the body, and marks every answer, an extractor's refusal and the router's own 405 included. `/oauth/authorize` reads its parameters through the strict parser (`auth::oauth::Params`), and `/oauth/token` will: a malformed escape or a value that is not UTF-8 fails the whole request, and a recognised parameter sent twice is refused before any value is read (`resource` twice is `invalid_target`, whatever else is repeated). It is a type, not a port: there is one implementation and nothing to substitute. When the store is full it first drops expired requests and approved ones whose code has expired, then the oldest request nobody has read, where the pending sign-ins (`AppState.logins`) refuse: an anonymous caller can open requests without end, and the unread ones are nobody's. Reason: the request never travels in a URL, so nothing the client sent can be altered on the way, and what a request and a code are bound to is a rule of the domain.
- **Every MCP token belongs to a connection, and every transaction that touches a person's connections takes that person's row first (kb/ADR-0029 R5, R8, R9).** A connection (`connections`, migration 2005; `reeve_identity::Connection`, with `is_live`) is a person, a client, a scope (`read` or `write`) and an end thirty days after the approval; `tokens.connection_id` is set exactly for an MCP token, with a foreign key on `(connection_id, owner)`; `refresh_tokens` holds hashes, one live row per connection, and the newest `used_at` is when the connection last refreshed. Who revoked a connection is in its activity entry, not in the row. `POST /oauth/token` (`crates/reeve-server/src/auth/token.rs`; the switch, POST only, a form of at most 16 KiB, RFC 6749 section 5 JSON out with `no-store`, never the API's envelope, nothing the caller sent in a log line) calls `exchange_code`, which redeems the code in memory and creates the connection and its first pair, or `refresh_tokens`, which marks the refresh token used and issues a new pair; a refusal rolls the mark back, and a token that was already used revokes the connection with a `connection_revoked` entry by `system` (no grace period). `client_id` is required at the exchange and optional at a refresh; a request that tries to authenticate is `invalid_client`. `authenticate_mcp` refuses a token whose connection is not live on every call, and `McpPrincipal` carries `connection_id`, `client_id` and `scope`. The lock rule has two levels: the person's `users` row first (`TokenStore::lock_user`, or the `ON CONFLICT DO UPDATE` of `set_disabled` and `ensure_user`), the activity entries last; whoever holds the row is alone with that person's connections, MCP tokens and refresh tokens, so nothing in between needs an order, and `crates/reeve-server/tests/oauth_disable.rs` probes it for some flows only: it goes red when a refresh or a disable writes before it holds the row, when a refresh or an exchange issues while a disable holds it, and when a disable records before it writes (the developer command and `connections-revoke-all` are not probed). `/mcp` calls take no lock. `disable_user` revokes the person's live connections in the same transaction (enabling revives none), and `reeve-server connections-revoke-all` revokes everyone's after a restore; every revocation writes `connection_revoked` through one function, `record_revocations`. The exchange deletes the connecting person's own connections that stopped more than thirty days ago, which is what bounds the rows of spent refresh tokens. Reason: issuing can never slip past a disable or a revocation, and no two of these transactions can deadlock.
- **A connection is listed once and revoked as a whole (kb/ADR-0029 R9).** `GET /api/v1/connections` answers the caller's own (an admin may pass `owner`): the live ones, and those that ended or were revoked in the last thirty days, filtered by date in the query, never by relying on old rows having been deleted. `DELETE /api/v1/connections/{id}` is the owner's and any admin's, with either kind of token, since it only reduces access; whoever may not revoke a connection gets the 404 of one that does not exist, and so does an ended one. Revoking writes the connection row only: its tokens stop through `authenticate_mcp`'s check at their next use. `revoke_connection` reads the connection to learn its owner, takes the owner's row, and revokes through the same store method and the same `record_revocations` as disabling and the restore command. The web client shows connections under "Connected apps" on the tokens page and per person on the users page, and follows live updates; the CLI has `reeve auth connections [--owner <email>]` and `reeve auth connections revoke <id>`. Listing gives an admin sight of other people's connection metadata, which the later observation on kb/ADR-0029 names and accepts. Reason: an admin who must cut a connection has to be able to find it.
- **The server has a clock, `AppState.clock`.** `Caller`, `McpCaller` and the OAuth routes read it once per request and pass that instant on; the approval page's API routes take the instant from their `Caller`. It is the system time; a test harness may replace it with a fixed instant that moves only by `Clock::advance` (`Harness::with_fixed_clock`, which starts at a whole microsecond, as PostgreSQL stores times). The sign-in routes, the event stream and the webhook read the system time. Reason: requests live ten minutes, codes one and tokens an hour, and no test may wait or depend on how long it ran.
- **The access policy is the configured floor plus `allowed_entries` and `admin_grants`, loaded on every request and every event-stream batch, with no cache.** The floor is `allowed_domains`, `allowed_emails` and `admins` from `reeve.toml`; admins add entries and further admins in the identity tables (kb/ADR-0015). Sign-in, token issue, the role check and the stream all take the freshly loaded `AccessPolicy`, so a grant or a revoke applies to the next request. A database grant the floor no longer allows is kept, flagged not allowed, and grants nothing. Every access write takes the `reeve_access` advisory lock first and the activity lock last (the activity entry is recorded just before commit), so two writers cannot interleave and the lock order cannot invert. Reason: a revoked person must lose access at once, and a cache would be a second place to get that wrong.
- **The record check runs in the CLI** from a household checkout with `git show origin/HEAD:<path>` after a fetch; the server process holds no repository credential and never reads the household (in the reference stack the household and any read-only deploy keys sit in the server container for the CLI that runs there). Reason: the working tree may hold unmerged edits that must not count, and the server should not be able to read the team's repositories. The server only accepts a reference whose repository is one of the configured `[[repos]]` and whose path is relative, has no `..` component and does not start with `-`; the CLI independently refuses a repository name that is not one directory name. `not_found` is stored only when `origin/HEAD` resolved and the file is absent from that commit; a missing clone, failed fetch, unset `origin/HEAD` or unparsable front matter stores nothing and is reported `unreadable` (exit 1), so a misconfigured checker cannot flip accepted decisions back to blocked.
- **Only an admin's check stores `accepted`.** `record_check` takes `is_admin` from the route and refuses a non-admin's satisfying result with 403 `forbidden` before reading the row; every other result is stored from any caller. The CLI reports that refusal as `held` (exit 0), and `decision link --json` carries it in `immediate_check`. Reason: kb/ADR-0027 R3; a member's token, or automation acting under it, must not satisfy a decision by assertion, while results that only add a reason are harmless and corrected by the next run.
- **A required decision's planner fields are edited with `PATCH /decisions/{id}`; its reference only through `link`.** Title, decider, due and reversibility (kb/ADR-0013 R1) change under the decision's version and are logged `edited` with each changed field's old and new value (`fields`, `from`, `to`); the reference, PR url and check are never written by an edit, and `EditDecision` refuses unknown fields. `close_decision` takes a kind (`decided` | `withdrawn`) and no caller version; every close rule is on `RequiredDecision::close`, and planning stores `closed_kind` and `closed_via` itself (kb/ADR-0010 R3). An edit takes no role and never writes the check, so it needs no `is_admin`; a member may retitle a decision an admin's check satisfied, and the entry keeps that visible and attributable. Reason: kb/ADR-0004 R1 (the planner stores only the check result and the reference) and R3 (only a reference change resets the check).
- **A details-only initiative edit keeps a horizon that is no longer configured.** `check_horizon_change` (`domain/items.rs`) is the edit's rule (`edit_initiative` is its only caller): a horizon equal to the current one is always valid, and only a change is checked against `horizon_buckets`. Create and import check the bucket in `Initiative::new`, where every horizon is new. Reason: unlisting a bucket must not make every initiative in it uneditable.
- **Epics and initiatives list by creation time, then key number.** Both lists order by `created_at, length(key), key`, so items created in the same instant come out in key-number order, not lexicographic (`ABC-10` after `ABC-9`). Reason: a stable, numeric tie-break that a test can pin.
- **The scheduled check runs inside the server container.** A host systemd timer (`deploy/systemd/`) runs `docker compose exec -T server reeve-decision-check` every ten minutes with an admin's automation token on stdin; the script takes a lock in the `reeve-household` volume, enforces its own deadline on its whole process group, clones what `reeve-server repos` lists (partial, no checkout, into a temporary directory renamed into place when complete) and execs `reeve decision check --strict`, which fails on a held result. Existence on the default branch is read from the commit's tree, so an unreachable origin is `unreadable`, never `not found`. Reason: kb/ADR-0016 R3 (no third container) and kb/ADR-0016 R2 (no second list of repositories). An edit bumps the decision's version, so a check in flight when an edit (title, decider, due or reversibility) lands is refused with 409 (a close, which takes no version, still makes the check refused: the decision is closed): `reeve decision check` re-reads the decision after a 409 `conflict` (version changed) or a 400 `validation` "decision is closed" (it matches the error code, not the status) and reports it `skipped`, never a failure, even under `--strict`; `deploy/decision-check.sh` only passes that status through, and the next run checks the decision (see `deploy/README.md`).

## Interfaces and storage

- **OpenAPI is generated by utoipa from the protocol crate and snapshot-tested** (`UPDATE_SNAPSHOTS=1` regenerates it). **sqlx runs runtime-checked queries.** **Migrations are per crate with disjoint version ranges** (1xxx planning, 2xxx identity, 3xxx activity), composed by the server into one strict migrator. Reason: contexts own their tables, and a migration deleted from any crate must be detected (`VersionMissing`) rather than hidden by `ignore_missing`.
- **Idempotency keys are stored per item table (comments included, as a nullable column with a partial unique index) and never expire.** Reason: a retried create can always be recognised, and there is no expiry job to run. The one exception is an upload's key, which lives as long as its attachment row: a key whose upload was deleted, or swept unclaimed after seven days, uploads anew.
- **One API route takes a raw body: `POST /api/v1/attachments`** (the only other handler that reads the request itself is `/mcp`, below). The image is the body (`application/octet-stream`, typed as a binary string), the filename and idempotency key are query parameters, `DefaultBodyLimit` is raised to 10 MiB on that route alone, and `ApiBytes` (`crates/reeve-server/src/extract.rs`) turns an over-limit body into a 413 `validation` envelope. Serving streams the stored chunks one pool query at a time, with the headers and access rules of kb/ADR-0023. Reason: a base64 JSON body would grow every image by a third, and a raised limit on every route would let any JSON write be 10 MiB.
- **Response envelope: ok, refused with reasons, or error with a code.** CLI exit statuses are 0 (ok), 2 (refused), 1 (error). Reason: agents branch on the status, and a refusal is an answer, not a failure.
- **The MCP endpoint is a third interface, beside the API and the browser routes.** `/mcp` is always mounted and answered by Reeve's own handler (`crates/reeve-server/src/mcp/`), which takes the raw request and runs its checks in a fixed order: the `[mcp] enabled` switch (404, plain text), POST only (405), the `Origin` check (403), the caller (401 with `WWW-Authenticate: Bearer resource_metadata="…"`), a JSON body of at most 1 MiB, one JSON-RPC message, then the protocol checks. It serves MCP revisions 2026-07-28 (stateless) and 2025-11-25 (the `initialize` handshake, served without a session) and always answers one JSON object; its errors are `McpError` before the message is parsed and a JSON-RPC error (`RpcError`) after, never the API's envelope. The HTTP statuses of a JSON-RPC error are partly the specification's and partly this server's choice. On 2026-07-28 the specification gives 404 for an unknown method and 400 for a header mismatch, an unsupported version and a missing required `_meta` field; 400 for other invalid params (an unknown tool) and 500 for an internal error are this server's. On 2025-11-25, which keeps 404 for an expired session and names no status for a JSON-RPC error, an error for a classified request (an unknown method, an unknown tool, a `tools/call` without a name) is answered with HTTP 200, a body that does not parse or a message that cannot be classified stays 400, and an internal error is 500; these are this server's choices. In both revisions a notification gets no body once it has been parsed: 202, or the failing check's status alone. A tool's own failure (a bad argument, what the planner said no with) is not a JSON-RPC error but a result with `isError: true`, HTTP 200. `mcp/protocol.rs` knows nothing about Reeve. Reason: Claude starts sign-in only on a 401, so the caller check comes before every protocol check, and an extractor would run before the switch and the origin check (kb/ADR-0029 R1, R2).
- **An API route and its MCP tool share one action.** `crates/reeve-server/src/actions/` holds everything between the caller check and the response, with one shape: `async fn <name>(state: &AppState, who: &Acting<'_>, <the input its route takes>) -> Result<<Dto>, AppError>` (a create answers the DTO and whether this call created it, which is the insert's own answer; a tool's receipt needs it). The input is the route's (its path, its query struct or its body), not the tool's type: the route passes what it parsed, and a tool is an adapter that turns its own narrower input into the route's and calls the same action. `Acting` carries planning's `Ctx` and the access policy, and has one constructor that both callers use; a caller with no client is an API caller. `Acting::write_key` decides the space an idempotency key is stored in: an MCP caller's as `mcp:<email>:<key>` (no key is built for an email with a colon, which would make that format ambiguous), an API caller's as it is, and an API caller may not send a key starting with `mcp:`. The prefix is reserved for the keys of a story or a comment, the two things a tool creates; a tool that creates anything else must extend the reservation to that route first. A tool's arguments deserialize into a `reeve-protocol` `…Input` type (flat, `deny_unknown_fields`), its `inputSchema` is generated from that type by utoipa, and the tool list is snapshot-tested (`UPDATE_SNAPSHOTS=1 scripts/test.sh -p reeve-server --features reeve-server/static-oidc --test mcp the_tool_list`). Reason: a tool must run the same handler and the same validation as its route (kb/ADR-0029 R1, R12).
- **The MCP tools are the set of kb/ADR-0029 R10, one per CLI command.** Nine read: `search_items` (`reeve search`), `list_stories` (`story ls`), `get_story` (`story context`), `list_epics` (`epic ls`), `get_epic` (`epic show`), `list_initiatives` (`initiative ls`), `get_initiative` (`initiative show`), `list_decisions` (`decision ls`) and `get_sprint` (`sprint show`). A route's query struct lives beside its action (`actions/stories.rs` holds `StoryQuery` and the paging check), so neither `mcp/` nor `actions/` depends on a route file. An adapter does on the server what the CLI does on the client: `mine` is the caller from `Acting`, `open` is `done=none`, and `get_sprint` without an id reads the sprint list, takes the active sprint, else the draft, and reads it again by id. Every answer is bounded, in `mcp/tools/bound.rs` and by summary types in `reeve-protocol`. A list that is not paged is capped in rows (200 summaries: `EpicSummary`, `InitiativeSummary`; 50 whole required decisions; the search's own 50 hits), then fitted to one answer budget (`fit`: rows are dropped from the end while the rows are over 60 000 bytes), and says how many rows it left out (`omitted`). The story list answers a page of `StorySummary` (25 by default, at most 50), fitted the same way, and `next_offset`, counted from the rows sent. One item is answered as its API type with every long text cut (its own at 10 000 characters; every text that comes along, a goal's texts and a decision's closing reason included, at 2 000). For whatever is still too large (one item with a pathological collection), the dispatch refuses any answer over 70 000 bytes with a tool error; such an item cannot be read over MCP. An answer is sent twice, as `structuredContent` and as the same JSON in one text block, and is always a JSON object. In a tool's input schema an optional argument is its plain type, absent from `required` (`tools::input_schema` flattens utoipa's nullable forms). The registry is built once, in `build_state` (`AppState.mcp_tools`). Reason: a chat reads an answer into a limited context and a client cuts what is too long, so an answer must be small and say what it left out, and a tool must not have powers its CLI command lacks (kb/ADR-0029 R1, R10).
- **Four tools change something: `create_story` (`story create`), `edit_story` (`story edit`), `add_comment` (`comment add`) and `move_story` (`story mv`).** A tool needs the `write` scope exactly when its `readOnlyHint` is false (`Tool::allowed`; there is no scope field): `tools/list` shows a connection only the tools its scope allows, so its `cacheScope` is `private`, and calling a tool the scope does not allow is HTTP 403 with `WWW-Authenticate: Bearer error="insufficient_scope", scope="write", resource_metadata="…"` in both revisions (the body is a JSON-RPC error with this server's own code -32003). After the scope and before the arguments, a call to a write tool is counted against the person: at most 30 in any ten minutes across the person's connections, refused calls and repeats included, held in memory (`mcp/limit.rs`, each person's own instants, pruned, checked and extended under one lock; a call is stamped with the server's clock when it is reserved, after its body was read, never with its caller's instant, and the limit's time is the clock's plus every step back the clock has made, so it never goes back and a step back of the clock refuses no one for longer than the rest of their window) and told to the model with the time to try again. Each tool's input is a type of its own that withholds what a chat may not send (the override reason, the rank, the external reference, attachments) and refuses unknown fields. `move_story` always passes no override reason, and `actions::move_story` refuses one from any caller that came through an MCP client, so a story that is not ready is never moved into work from a chat. `edit_story` takes clearing as a flag (`detach_epic`, `clear_owner`), merges criteria and labels as the CLI does, and refuses a text that ends with the cut marker (`get_story` always cuts a long text, so such a text is edited in the CLI or the web client). Every refusal is bounded once in `call_tool` (`tools::bounded`) whichever tool or action said it. A write answers a receipt (`StoryReceipt`, `CommentReceipt`: key or id, title, state, version, `created`), never the item, so the last guard cannot refuse an answer after its write; a repeated comment's receipt names no target, since its key may have made the comment on another item. Reason: a chat reads text other people wrote, so what a planted instruction can do is bounded by the tools, the scope and the limit, never by the model's judgement (kb/ADR-0029 R7, R9, R10, R12; kb/ADR-0027 R2).

## Browser and live updates

- **The browser session is an interactive token in an `HttpOnly` cookie.** Signing in with Google issues an interactive token labelled `web session` (expiring after `session_days`) and sets it as `__Host-reeve_session` (`Secure`) on an https instance, `reeve_session` on a loopback http one; the extractor reads only the name the instance issues, bearer header first. Reason: no new session table, and revoking the token or disabling the user ends the session like any other token (kb/ADR-0015 R6).
- **Production discovers only `https://accounts.google.com`.** `make_google_oidc` passes the constant issuer and the 60 s minimum refresh gap and 24 h maximum metadata age; the only way to another issuer is `make_google_oidc_for_tests`, compiled only under the test-only `static-oidc` feature that the Dockerfile never enables, and `[oidc]` has no issuer field (it refuses unknown keys). Reason: sign-in goes through Google (kb/ADR-0015 R1), and the adapter production runs is the same code the tests drive against a fake issuer.
- **Cookie-authenticated writes carry `X-Reeve-Client: web`.** Any cookie request other than GET or HEAD without it is refused; bearer requests are exempt; the server sends no CORS headers and the cookie is `SameSite=Lax`. Reason: a cross-origin page cannot add a custom header without a preflight the server never answers, so the header is the CSRF defence.
- **The event stream polls the committed activity log.** `GET /api/v1/events` sends `event: activity` frames (id = entry id, data = `ActivityEntryDto`) for entries with an id above the last sent, every two seconds, resuming from `Last-Event-ID`; it re-authenticates the session on every tick and ends when it dies. Ids become visible in id order because the activity writer takes a transaction-level advisory lock immediately before its insert and holds it until commit. Hence the rule: **a mutation records its activity entry last, immediately before commit**, so the lock serialises only the commit tail and never the mutation's own work. Reason: polling committed rows publishes after commit by construction (kb/ADR-0010 R5), needs no in-process bus, and works with more than one server; without the lock a later id could commit first and a resuming stream would skip the earlier one forever. The web client refetches the open view on any entry and on every (re)connect, 500 ms after the last change with a 5 s max-wait after the first change of a burst, so a steady stream refetches every few seconds rather than never. A hidden tab refetches nothing: a change while hidden (or a refetch already scheduled when the tab is hidden, which is cancelled) marks the view stale, and the tab refetches once when shown. It does not filter by entity: the dependency graph is the whole tree (a story change moves initiative progress, a discovery mark changes every descendant's readiness).
- **The client is static, embedded and typed from the snapshot.** `web/` builds with the static adapter into `web/build`, which `rust-embed` puts into `reeve-server` (no Node at runtime, kb/ADR-0006 R1); the server sets the CSP with a hash per inline script. `web/src/lib/api/schema.d.ts` is generated by `npm run gen` from the committed OpenAPI snapshot, never written by hand, and CI fails when it drifts. Reason: a wire change is one diff in `reeve-protocol` plus two generated files, and the client cannot name a shape the server does not return (kb/ADR-0006 R2, R3).
- **Edit forms send only the fields the user changed and merge per field after a conflict.** The diff is against the values the editor opened with; a 409 reloads, says so, keeps the user's changed fields and takes the reloaded value of every other, and the base becomes the reloaded version (`web/src/lib/forms.ts`, and `followBase` in `web/src/lib/editorBase.ts`). Creates follow the draft-key rule of `web/src/lib/idempotency.ts`. Target month is validated in the client only. Reason: a retry never reverts a colleague's field, and a refetch never overwrites a draft.
- **The create forms and details editors added in m2e show their errors in the form.** These are the planning page's "New initiative", `NewEpicForm`, the initiative and epic "Details" editors and DecisionList's decision editor: the message sits in a `role="alert"` paragraph inside the form, coloured `var(--danger)` (the token in `web/src/app.css`, with a dark-mode value). A conflict on a page's details editor is the exception: it reloads the page, so its text goes to the page notice; DecisionList's conflict text stays in its editor, except when the reload shows the decision closed: the editor goes, so the message goes to the closed row's errors. The older forms still report through `write()` into the page or drawer notice: the brief editors, the epic page's "New story", the "Require decision" forms on the initiative page, the epic page and the story drawer, and the drawer's field forms. An editor that replaces its toggle moves focus to its first field when it opens and back to the toggle when it closes (Cancel or a save), and back to its first field after a failed save, in each case only if focus is still in the form or on the page (`web/src/lib/focus.ts`). Reason: an error outside the form is out of sight on a long page and not announced, and focus left on a removed button drops to the top of the page.
- **Every epic, initiative and label choice in the client uses `web/src/lib/ui/Picker.svelte`.** A searchable combobox over options the page passes in (`lib/picker.ts`: `keyed`, `narrow`); it never fetches, and its empty choice reads "No epic", "No initiative" in an edit field and "any" in a filter. Reason: a native `<select>` cannot be searched, and a long list of epics must be; one component keeps the keyboard behaviour (Enter picks, Escape closes, Ctrl+Enter is the page's) the same everywhere.
- **Dropping an item marked as a duplicate writes one comment under the deterministic idempotency key `triage-dup:<key>:<dup>`.** The key is built from the triaged story and the story it duplicates, never from a random id or the version, so a retried drop, or a drop again after Undo, is recognised by the comments' idempotency column and leaves one "Duplicate of GRA-y." comment. Reason: the drop may be sent more than once, and a duplicate comment is noise a reader cannot tell from a second opinion.

## The TUI

`reeve tui` (`crates/reeve/src/tui/`, kb/ADR-0011) is an HTTP and event-stream client like the browser: protocol types
only, no store. It is a reducer of feature slices (`board`, `moves`, `set_epic`, `urgent`, `live`) under a core that routes messages;
an update never does I/O, the runtime runs its effects and returns results as messages. Writes are not optimistic.
Freshness is by request order, not story version alone: the core numbers every request when it is sent, and a board
load sent before a write completed is dropped. It authenticates only with the stored login (`REEVE_TOKEN` is never its
credential) and runs read-only on an automation token. The driver takes an injected backend, input stream and side
effect sink, so tests run it headless: pure update tests, a scripted server, the real server, and a pty smoke.

## Import, export and pull-request links

- **The Jira import is create-with-state behind a switch.** `POST /api/v1/import/*` creates initiatives, epics, stories and comments in the state they had in Jira (delivery, resolution, owner, labels, criteria, comment author and date, a discovery mark by the importing admin above an in-flight story) and logs each as `imported`, never `override`: the gate is not consulted and `move_story` is not called. Every import handler answers 404 unless `[import] enabled = true` (checked before the caller, so a switched-off instance reveals nothing), and then only an admin with an interactive token may import. The external reference is the idempotency key: a reference that exists answers `created: false` and writes nothing. An item reference names one Jira issue, so it is looked up across all three item types: one already imported under another type is refused (`validation`, "SCRUM-30 is already imported as story JPD-12") and never becomes a second item; comment references are their own namespace. An item's reference must parse as a key reference (`JPD-77`) and must not start with the instance prefix; a comment's author and body must not be blank; titles are at most 200 characters (the CLI truncates and warns). Items are validated before they are looked up, so a re-run under a changed configuration can answer a validation error instead of "existing". Reason: grandfathering must not inflate the override count (kb/ADR-0027 R2), and the switch keeps admins from creating in-progress stories or back-dated comments after import day.
- **Pull-request links are planning data, updated by the webhook as `github` via `Via::System`.** `POST /webhooks/github` (outside `/api/v1`, authenticated by the `X-Hub-Signature-256` HMAC, never by a token) upserts a story's pull request and records `pr_linked`, `pr_unlinked` or `pr_updated`. It has no path to `move_story` and never touches delivery, resolution or version: a merged pull request leaves the story where it was. Reason: pull-request status is a cache of GitHub's state, not a delivery decision (kb/ADR-0002 R4), and the PR table belongs to planning with the story as parent (kb/ADR-0010 R3).
- **The export is one read-only `REPEATABLE READ` transaction across contexts.** `GET /api/v1/export` (admin, interactive token) passes one transaction to the transaction-taking export readers of planning, identity and activity, so the document is one snapshot; its DTOs are built from reads on that transaction, never through the pool (the story DTOs by `story_dtos_in`, whose assembler reads on the caller's transaction). The route and the operator's offline `reeve-server export` call one function, `export_document`, so the two documents cannot drift; the offline export connects with `default_transaction_read_only=on`, never migrates, and refuses a database whose applied migrations (versions and checksums) are not exactly the binary's. It holds emails and roles, never token hashes, secrets or configuration. `exported_at` is the request time, taken before the snapshot's first statement. Reason: a backup that mixes two states of the world cannot be trusted, and the backup must not leak credentials.
- **The restore source is a `pg_dump` archive; the export is the readable record.** The dump carries what the export leaves out by design (token hashes, idempotency keys, the key sequence, the migration table), so a restored instance keeps its sessions, deduplicates retried creates and continues its keys; a restore from the export would need a second writer for every table and would lose all of that. `scripts/backup.sh` publishes a dump and an export together or not at all; `deploy/README.md` documents the restore (checked with the server stopped) and a rehearsal (`scripts/restore-rehearsal.sh`) for the compose stack; `crates/reeve-server/tests/backup_restore.rs` runs the same PostgreSQL commands through the same pipes in the test container. Reason: the parent design makes a rehearsed restore a hosting precondition, and only a dump restores everything (kb/ADR-0007 R1, kb/ADR-0016 R3). The restore ends every MCP connection before the server starts, with `reeve-server connections-revoke-all` (a dump rewinds refresh tokens).
- **Every key input resolves through one `Handlers::resolve`; `resolve_ref(raw, ItemType)` is a wrapper over it.** `resolve_any`, the webhook's branch-token lookup and the decision-target type check are wrappers over it too, with precedence unchanged, and the untyped native check is one statement. Path segments, parent fields, `blocker` (the body of `POST …/blocks` and the path segment of `DELETE …/blocks/{blocker}`), `rank.before` and the typed list filters all go through it: native keys come first: a key of the instance prefix is returned as is, and a key of any other prefix is returned when an item of that type has it (items issued before a `key_prefix` change keep their keys); only then is anything in key-reference grammar looked up as that item type's `external_ref`, and everything else is NotFound. So an external reference never shadows a real key, even one issued under an earlier prefix. The untyped decision target (`on` of a decision and the `?on=` filter) goes through `Handlers::resolve_any(raw)` instead, the single "any item" path: native keys of every item type first, then the external reference of a story, an epic, an initiative, so a story whose `external_ref` is `OLD-1` never shadows an epic keyed `OLD-1`. The webhook resolves branch names under `[github] legacy_prefixes` (the Jira delivery project's key, such as `SCRUM`) through the same `external_ref` lookup. One input is not a key input: `GET /activity?entity_key=` filters the log literally and takes instance keys only, because an entry records the instance key. Reason: Jira keys stay usable after the import (kb/ADR-0002 R5) without a second key scheme, and the CLI passes key arguments through as strings.
- **The repository publishes images; an operator deploys them.** `release.yml` publishes `ghcr.io/mindful-stack/reeve:<sha>` for every push to `main` that changes a build input (never `latest`) and checks that the image runs and carries the tools its one-off jobs need; hosts, secrets and the deploy job live with the operator, outside this repository. `reeve-server migrations` lists the image's migration set, which a deploy compares with the database's ledger as sets, never maxima (the ranges per context let a new migration sort below the current maximum). Backups are one exported snapshot for the dump and the export (`scripts/backup.sh`, `export --snapshot`). Reason: one image serves every operator, and no operator's host details live in the code (kb/ADR-0016 R3).
